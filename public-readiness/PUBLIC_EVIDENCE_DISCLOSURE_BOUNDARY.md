# Public Evidence Disclosure Boundary

Shadow-Tech2030 separates **internal assurance evidence** from **public validation evidence**.

## Publicly acceptable

The following categories may be published when sanitized and non-sensitive:

- aggregate readiness metrics;
- pass/fail counts;
- public methodology descriptions;
- public limitation statements;
- hashes of published artifacts;
- high-level validation outcomes;
- public evidence provenance;
- externally shareable reports that contain no proprietary implementation detail.

## Internal only

The following remain internal unless explicitly approved for controlled disclosure:

- detailed risk registers;
- detailed vulnerability records;
- internal gap and finding narratives;
- management decision records;
- supplier assessments;
- access reviews;
- personnel lifecycle records;
- detailed remediation notes;
- internal control implementation details;
- private repository metadata that could expose sensitive operations.

## Never public

The following must not be published merely as validation evidence:

- proprietary source code;
- private keys;
- authentication secrets;
- production credentials;
- secret configuration values;
- private cryptographic key material;
- sensitive implementation details that would materially weaken security.

## Principle

Public transparency should demonstrate what can be verified **without turning transparency into disclosure of protected intellectual property or sensitive security information**.

**Evidence over claims. Transparency without disclosure.**
